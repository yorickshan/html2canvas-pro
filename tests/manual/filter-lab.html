Measure the cost, not just the output

Run the benchmark ↗

Compare the production SVG surface helper with an opacity-only copy and a benchmark-only Canvas filter alternative. The full-capture suite also compares published 2.4.3 with this draft, including no-effects controls, sparse and nested layers, and an explicitly labeled memory-budget fallback.

CI measurements: Chromium 148 and Playwright WebKit 26.4 on Ubuntu, 4 vCPUs. Medians below include full output readback, after two warmups and nine measured samples. PR head ec0183e; this is Linux WebKit, not a macOS Safari or WKWebView measurement. These are observations on a shared runner, not a universal speed guarantee.

The high-entropy SVG round trip has a material cost. Noise stresses PNG encoding and the large SVG data image; it does not mean every photograph costs this much. A native fast path is worth evaluating, but is not enabled in the production renderer by this benchmark. Canvas filters are explicitly unsupported in the tested WebKit runtime, not counted as fast no-ops.

Full 2000 × 2000 capture without effects measured 66.6 ms before / 66.8 ms after in Chromium, and 74.0 / 72.0 ms in WebKit. With combined effects it measured 70.3 / 196.2 ms in Chromium and 868.0 / 278.0 ms in WebKit. The release's combined result has incorrect opacity (center alpha 252 instead of 128), so filtered rows are not equivalent visual workloads. The over-budget case is reported separately and must not be interpreted as successful filtering.

The benchmark page records first observations, median/p95, encoding/decoding and all raw samples, with JSON export/import and a Stop button.
